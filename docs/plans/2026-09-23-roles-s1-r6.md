### 2.4 README

Add a section `### Roles` directly before `### Availability`
(`README.md:1412`), under `## Candidates`, after `### Policy`. It covers,
in plain prose, with one JSON example:
- **The model.** A role is what a job *is*: its shape (`writer`/`reader`),
  whether it is gated, and its agent definition per harness kind. A candidate
  is a harness/provider/model. Each role picks its own candidates, in order,
  at its own tier.
- **`roles.json`**, at `~/.config/relay/roles.json`. Its fields: `shape`,
  `gate`, `definitions.<kind>.agent` / `requires`, `candidates` and `tier`.
  - Built-in rows (builder, reviewer, researcher) are defaults, and a row
    overrides them field by field.
  - A new role must be a `reader` for now, and runs with `relay ask --role
    <name>`.
  - Unknown keys are warnings, not errors.
- **Custom definitions.** Where each harness looks for them:
  - claude: `~/.claude/agents/<n>.md`
  - opencode: `~/.config/opencode/agents/<n>.md`
  - agy: `~/.gemini/config/agents/<n>.md`
  - codex: `~/.codex/<n>.config.toml`

  relay never installs or refreshes a custom definition. A missing one gates
  its candidates for that role only, and doctor lists it.
- **Bring your own agent.** Everything relay's round protocol needs is in the
  prompt relay sends: the working tree and its `git status` check, the plan
  path, the report path, the done marker and the closing `relay` block. A
  custom definition only shapes behaviour. `requires` names the definitions
  your agent dispatches to (the shipped builder requires `researcher`).
- **Migrating.**
  - Without `roles.json`, relay keeps reading `candidates.json` `roles`/`tier`
    and `policy.json` `order`/`tier`, and nothing changes.
  - `relay roles init` writes `roles.json` from them (`--dry-run`,
    `--force`).
  - Once the file exists, those fields are ignored, and `relay doctor`
    lists them.
  - Delete them only after every relay process on the machine is upgraded:
    an older relay doesn't know `roles.json`.
- **Seeing it.**
  - `relay roles` lists shape, candidates, tier and definitions.
  - `relay policy` shows `(roles.json)` per role.
  - `relay status --json` has `builder_definition` for a custom builder.
- **Remote builders.** A server resolves roles from its *own* config.

Also:
