## 1. System overview

`log.jsonl` is append-only, one JSON object per line
(`internal/store/log.go:214-242` `appendLog`), and every reader
(`relay log`, the ui log tab, `status`, `statusline`, hooks) reads the
whole file. There is no stable way to say "entries since the last one I
saw". After this round every entry carries `Seq` (1-based per binding,
assigned by the store on append, never by callers); a file written before
this change reads back with `Seq = line number`, so nothing is rewritten;
`relay log` grows `--after N`, `--json` (NDJSON) and `--follow`; and
`status --json` reports each binding's `last_seq`. `confirmIndex`
(`log.go:327-354`) rewrites the file from decoded entries, which now carry
`Seq`, so a rewrite preserves numbering. `ForkState` (`store/fork.go:90-114`)
copies a prefix of entries verbatim, so a fork's numbering equals its
source's for the copied rounds -- the invariant is "monotonic per file",
which holds. `internal/ingest` keys events by absolute line index already
(`cursor.go:55-99`); `Seq` equals that index for every file, old or new.

## 3. Data structures

```
// internal/store/log.go
LogEntry.Seq int `json:"seq,omitempty"`
    // 1-based position of the entry in its binding's log; assigned by appendLog, filled on read for files
    // written before Seq existed. Callers never set it; appendLog overwrites whatever a caller passed.

// internal/relay/status.go
BindingStatus.LastSeq int `json:"last_seq"`   // Seq of the newest entry; 0 when the log is empty (no omitempty: a consumer reads 0 as "nothing yet")
```

## 6. Error handling

- `appendLog`'s pre-read failing for a reason other than not-exist is the
  append's error (today a write error is fatal too).
- `--after` negative -> usage error, exit 2 (`exitCodeErr{2}` as the other
  flag errors do).
- `FollowLog` on a binding that disappears mid-follow returns nil (exit 0);
  the CLI prints nothing extra.
