## Working efficiently (read this before step 1)

Your provider has about **3 s of round-trip latency per model step**,
whatever the step does. Generation itself is fast. The last comparable
round took 307 steps, and 261 of them made a single tool call. The cost
of this round is its **number of steps**, so:

1. **Batch independent tool calls in one step.** When you need several
   files, ranges or searches that don't depend on each other, issue them
   all as parallel tool calls in the same response. The same goes for
   independent edits to different files.
2. **Read once, from the locations given.** This plan names files,
   functions and line ranges. Read each file you will edit once (the named
   ranges, or the whole file if it's under ~400 lines) before editing it.
   Don't grep for things the plan already located, and don't re-read a
   range you have already seen unless you edited it.
3. **Edit in as few calls as possible.** Make every change to a file in one
   edit call (several hunks), or rewrite the file when most of it changes.
   Prefer one scripted edit (a short `python3` or `perl` over named ranges)
   to many single-hunk edits when the change is mechanical.
4. **One tight build/test loop.**
   - Iterate with `go build ./... 2>&1 | head -80` and focused
     `go test ./<pkg> -run '<names>'`.
   - Fix **every** error a run reports before running again.
   - Run `make check` once when you believe you are done, and once more
     only if it fails.
5. Don't run `git status`/`git diff` between edits for reassurance. Run
   them at the start and before the commit.

Another builder is editing non-Go files (README, Makefile, scripts) in
parallel. Touch only `internal/e2e/` and, if unavoidable, test-only
helpers. The Makefile's `e2e` target will run
`go test ./internal/e2e/ -run TestHeadlessE2E -count=1`, so name the test
`TestHeadlessE2E`.

## What the test does

`internal/e2e/headless_test.go`, **no build tag**, so plain `go test ./...`
runs it in CI. No network, no real harness, no herdr. It uses only the
`relay` code in-process plus a fake harness binary.

1. **Fake harness.** Build, or write as a script into `t.TempDir()`, an
   executable named like a real harness kind the candidate table knows
   (e.g. `claude`), and put it first on `PATH`. When relay runs it for a
   round, it must:
   - read the plan path from its arguments or prompt the way the real
     harness form does (find how the headless launch passes it,
     `internal/harness` Print form);
   - write a small report to the report path;
   - make one commit in the worktree;
   - create the done marker;
   - print a minimal valid stream line if the headless reader needs one.
   
   Mirror how existing headless tests fake a harness, if they do. Reuse
   before inventing.
2. **Isolated state.** `HOME`, `XDG_CONFIG_HOME` and `XDG_STATE_HOME` go
   under `t.TempDir()`. Write a `candidates.json` and `policy.json` there
   naming the fake harness. Use a throwaway git repo with one commit as the
   project.
3. **Planner registration.** Run `relay planner init --hook claude`
   in-process (call the command function, don't exec a binary) with a
   canned `SessionStart` input (`source: startup`, a fixed `session_id`)
   and `CLAUDE_ENV_FILE` pointing at a temp file. Assert that the file
   gains `export RELAY_PLANNER=<id>`, and set that env for the rest of the
   test.
4. **Channel.** Start the `relay mcp` server in-process on a pipe pair,
   `CLAUDECODE=1` with the host pid of the test process. Use the
   stdio JSON-RPC the MCP server speaks: initialize, then wait for
   notifications. Assert that its claim file exists for the planner id.
5. **Round.**
   1. `bind` (or `add`) a headless binding on the throwaway repo.
   2. `send` a one-line plan.
   3. Drive the daemon tick in-process until the round closes (bounded:
      fail after 60 s, never hang).
   4. Assert that the MCP client received a `kind="report"` channel
      notification whose body contains the fake report's text.
6. **pull / done.** `pull` shows the report, and `done` marks the binding
   done.
7. **`/clear`.** Run `relay planner init --hook claude` again with
   `source: clear` and a **new** `session_id`, from the same host. Assert
   the same planner id, the new session current, and the old one in
   `sessions`.

Every wait is bounded with a deadline and a clear failure message. The
test must fail, not hang, when any step breaks. Clean up child processes
with `t.Cleanup`.
